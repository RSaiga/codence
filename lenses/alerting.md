# alerting — 知らせの観点 / Alerting lens

変更を、下の汎用の項目と、プロジェクトが足した項目（`profile.md` の `lenses.alerting.catalog`。無くてよい）に照らして読み、
提供者が失敗をユーザーからの連絡で初めて知る箇所（遅れて知る、知らないままの箇所）を指摘する。知らせはユーザーが気づくより先か同時に届かなければならない
（DORA の proactive failure notification、Google SRE の symptom-based alerting）。
Point out failures the provider would first hear of from users, or never (DORA's proactive failure notification; Google SRE's symptom-based alerting).

## 報告の口 / The reporting path

`profile.md` の `lenses.alerting.report` に、プロジェクトの報告の口（エラーの追跡サービスに送る関数、自動で送る包み・例外の処理）と、
そこから人に通知が届くこと、運営の見る通知の口（あれば）が書いてある。これを前提に読む。ログに残すだけでは届かない（`report` がログからの通知を書いていれば届く）。
`report` が無ければ、コードから報告の口を探す（Sentry などの初期化、送る関数）。見つからなければ、報告に「報告の口が無い」と 1 行書き、`ALR` の「高」は出さない。
Read with `lenses.alerting.report` (what reports, and that it pages someone). Logging alone does not alert unless `report` says logs do. With no reporting path, say so once and raise no high finding.

## 項目 / Items

番号は指摘の根拠に使う。プロジェクトの項目があれば、それを先に疑う。 / Cite the id; suspect the project's items first.

| 番号 | 項目 | 疑うところ |
|---|---|---|
| ALR-1 | 握りつぶし（swallowed error） | 失敗を既定値・空・`null` に変えて、正しい結果のように続ける（空の `catch`、`.catch(() => …)`、`.ok()`、`unwrap_or_default()`、捨てた `err`）。ユーザーには、失敗と分からないおかしな結果が見え、報告は出ない |
| ALR-2 | 報告の口を通らないエラーの応答 | 失敗を捕まえてエラーの応答・表示を返すが、報告の口を呼ばない。捕まえたことで、上の自動の報告にも届かない |
| ALR-3 | 誰も見ていない処理の失敗 | ジョブ・定期実行・Webhook の受け口・キューの消費・リトライを使い切ったときの失敗が、ログに残るだけ |
| ALR-4 | 黙った劣化 | 失敗に備えて用意した代わり（古いキャッシュ、前回の値、代わりの経路、一部を飛ばす）に切り替えて続けるのに、知らせが無い。ユーザーには古い・欠けた表示が出る。用意した代わりでなく、空や既定値で続けるのは ALR-1 |
| ALR-5 | 画面側の失敗 | エラーの境界・通信の失敗・処理されない Promise の拒否が、画面に出るだけで送られない |
| ALR-6 | 予期の分け方 | 予期しない失敗（依存先の障害、壊れたデータ、ありえないはずの状態）を、予期したもの（入力の誤り、見つからない）として扱い、報告しない |
| ALR-7 | 運営が同時に知る業務の失敗 | 利用者の操作で動く、お金・契約・権利の処理（決済、請求、返金、契約、解約、プランの変更）の失敗を、ユーザーには伝えるが運営に知らせない。または知らせに、誰の（利用者・テナント・プロダクト）、どの操作か、失敗の理由が欠けている。利用者の操作でない処理（起動、設定の読み込み）はほかの項目で見る |

## 読み方 / How to read

- **変更そのものは差分から読む。** 対象と差分は呼び出しが渡す（`review.md`）。追跡外の新しいファイルも対象。
- **失敗する場所を先に洗い出す。** 変更が呼ぶ I/O（DB、外部のサービス、ファイル）、パース、ジョブ。それぞれの失敗が、どこで捕まり、ユーザーに何が見え、報告の口に届くかをたどる。
- **上で自動に送られているかを確かめる。** 包み・フレームワークの例外の処理・ジョブの基盤が送るなら、捕まえずに投げる変更は指摘しない。その場所を実際に見る。
- たどるのに要るだけ検索してよい。検索は、確かめたいことを洗い出してからまとめて出す。

## 判定 / How to judge

- **確信度「高」には、気づく順番を書く。** 失敗（入力か出来事）→ ユーザーに見えるもの → 提供者に届くもの（何も無い・ログだけ）。書けなければ「中」か「低」にする。
  例: 外部の目録が落ちる → ユーザーには「見つかりません」と出る → 提供者には何も届かない。
- **「高」は、提供者がユーザーからの連絡より先に知る手段が無いときだけ。** 届くが手がかりが足りない、重さの付け方が違う、などは「中」か「低」（ALR-7 の手がかりの欠けは除く）。
- **症状で知らせ、原因では知らせない。** 知らせるのは、ユーザーに見える失敗と、再試行を使い切った失敗。再試行で回復した 1 回の失敗や内部の原因（1 回の時間切れ、CPU）に知らせを求めない。
  Alert on symptoms, not causes; never ask to alert on a failure a retry recovered from.
- **予期した失敗は知らせない。** ユーザーが自分で直すもの（入力の誤り、見つからない、権限が無い、競合、上限）を報告しないのは正しい。知らせを求めない（鳴りすぎると本物が埋もれる）。
  Expected, user-correctable failures must not alert; never ask for them to be reported.
  - **例外は ALR-7 の業務。** カードの拒否のようにユーザーが直す失敗でも、運営は同時に知る。届け先は当番の呼び出しでなくてよい（運営の見る通知の口で足りる）。見るのは、同時に届くかと、手がかりがそろうか。
    プロジェクトが `catalog` に足した業務も同じに扱う。 / ALR-7 flows are the exception: operators hear of them too, through any channel they watch.
- **出典の無い要件を作らない。** 言語パックの例は直し方の見本で、このプロジェクトの要件ではない。
- **誤検出を出さない。** 指摘の数より、指摘の正しさを優先する。

## 指摘の形 / Finding format

```
### [ALR-<番号> <項目>] — <file>:<line>  (確信度: 高/中/低)
- 何が問題か: <1〜2 行>
- 気づく順番: <高のときは必須。失敗 → ユーザーに見えるもの → 提供者に届くもの>
- 提案する手当て: <具体的に>
```

最後の行は `## LENS CLEAN` か `## LENS FINDINGS <件数>`（`discipline.md`「観点の約束」）。
